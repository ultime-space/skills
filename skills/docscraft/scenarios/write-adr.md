# 写 ADR

## 何时用

做出架构 / 分层 / 依赖 / 契约 / 规则体系的取舍，或需要留下“为什么”的证据。

## 输入

- 决策主题
- 背景与约束
- 备选方案（至少两个；只有一个要说明原因）
- 影响面：代码 / 规则 / 文档 / 发布

## 步骤

1. 查重：`docs/adr/` 是否已有相关决策；有则考虑 supersede。
2. 定编号：下一个递增编号，不复用。
3. 写背景：问题、约束、触发条件。
4. 列选项：每个选项写优点与代价。
5. 写决定：一句话说清选了什么。
6. 写后果：正面、负面、需要同步的规则 / 文档。
7. 写验证：命令 / 检查 / 观察指标。
8. 更新 `docs/adr/README.md` 索引。
9. 如果改变现行规则，同步更新 `rules/` 与 `AGENTS.md` 红线（同一变更）。

## 输出

- ADR 文件
- 索引更新
- 关联规则 / 文档变更
- 验证结果

## 验收

- 一条 ADR 只做一个决定
- 有背景、选项、决定、后果、验证
- 写了代价，不只写好处
- 旧 ADR 用 supersede，不删除
- 不复制规范全文
- 不含客户名 / 内部路径 / 密钥
