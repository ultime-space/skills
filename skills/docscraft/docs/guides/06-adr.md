# ADR（决策记录）

> 用途：记录“为什么这样选”，把决策与现行规范分开。
> 口径：一条决策一条记录；新决策 supersede 旧决策，不改写历史。

## 什么时候写

- 架构 / 分层 / 目录结构变化
- 引入或移除重要依赖
- 接口契约 / 数据模型取舍
- 规则体系变化（新增档位、废弃旧模式）
- 有争议、需要留下证据的决定

不写：

- 日常小改动
- 纯执行步骤
- 现行规范全文
- 没有备选方案的“通知”

## 文件

```text
docs/adr/
├── README.md          # 索引：编号 / 标题 / 状态
├── 0001-xxx.md
├── 0002-xxx.md
└── ...
```

编号递增，不复用。文件名用短横线，标题写决策，不写“讨论”。

## 模板

```md
# ADR-0001：<决策标题>

- 状态：proposed | accepted | superseded | deprecated
- 日期：YYYY-MM-DD
- Owner：<人 / 角色>
- 取代：ADR-0000（可选）
- 被取代：ADR-0003（可选）

## 背景

<问题、约束、触发条件>

## 选项

| 选项 | 优点 | 代价 |
|---|---|---|
| A |  |  |
| B |  |  |

## 决定

<选了什么，一句话>

## 后果

- 正面：
- 负面：
- 需要同步的规则 / 文档：

## 验证

<命令 / 检查 / 观察指标>
```

## 与其它文档的边界

| 文档 | 写什么 | 不写什么 |
|---|---|---|
| ADR | 为什么选、放弃了什么、后果 | 现行规范全文、操作步骤 |
| `rules/` | 现在必须怎么做 | 决策历史 |
| `docs/` | 稳定说明 / 操作 / 理解 | 未决讨论 |
| CHANGELOG | 用户可见变化 | 决策论证 |

ADR 可以链接 `rules/`；`rules/` 可以写“为什么见 ADR-000x”，但不复制论证。

## 状态流转

- `proposed`：提案，未定
- `accepted`：已采纳，现行有效
- `superseded`：被新 ADR 取代
- `deprecated`：不再推荐，但历史仍在

不要删除已采纳的 ADR；用新 ADR supersede。

## 写作要求

- 一条 ADR 只做一个决定
- 至少两个选项；只有一个选项时说明为什么没有备选
- 写代价，不只写好处
- 写需要同步的规则 / 文档
- 写验证方式；不能验证的标“待验证”
- 不写客户名、内部路径、密钥

## 索引

`docs/adr/README.md` 维护：

```md
| 编号 | 标题 | 状态 | 日期 |
|---|---|---|---|
| 0001 | 使用 X 作为请求层 | accepted | 2026-10-27 |
```

索引只做导航，不复制正文。

## 反模式

- ADR 写成规范全文
- 只写“决定”，不写选项与代价
- 新决策直接改旧 ADR
- 删除历史 ADR
- ADR 与代码 / 规则不一致，没人收敛
- 所有小改动都写 ADR，决策日志被噪音淹没
