# 规则治理

> 用途：让规则可维护、可执行、可过期，而不是越写越多。
> 口径：事实生成、约束机检、判断留人；没有 owner 的判断型规则不算稳定规则。

## 三类规则

| 类型 | 特征 | 维护方式 | 过期方式 |
|---|---|---|---|
| 事实型 | 字段 / props / API 形状 / 目录清单 / 类型 | 从源码、类型、配置生成 | 跟生成源同步；源变即变 |
| 约束型 | 必须 / 禁止 / 依赖方向 / 命名 | lint、CI、脚本 | 跟检查入口绑定；检查还在就有效 |
| 判断型 | 取舍、抽象时机、例外是否合理 | owner + 复核日期 | 到期降级为“参考” |

一条规则只能属于一类。混合时拆开：事实部分生成，约束部分机检，判断部分留人。

## 红线

`AGENTS.md` 只放少量红线，建议 ≤12 条。每条写法：

```text
禁止 X，因为 Y。
反例：<文件 / 场景>
```

要求：

- 动词开头，可判决
- 写“为什么”，不写口号
- 至少一个反例
- 不把整篇规范塞进入口

## Owner 与到期

判断型规则必须有：

```md
owner: <人 / 角色>
review: YYYY-MM-DD
```

到期未复核：

- 自动降级为“参考”
- 不再作为硬门禁
- 在规则表里标“过期”
- 由 owner 决定：续期 / 改写 / 删除

事实型规则不写日期，但写生成来源。
约束型规则不写日期，但写检查入口。

## 例外登记

例外必须写：

- 规则 ID / 名称
- 文件或范围
- 理由
- owner
- 到期

安全类红线不可豁免；发现密钥 / 越权 / 数据风险，先修复，不走例外。

## Canon 上收

跨项目规则不要一开始就上收。满足以下条件再考虑：

1. 在第三个项目出现
2. 机制相同，差异只在参数 / 适配层
3. 有人愿意维护 canon
4. 有验证方式（lint / 生成 / 示例）

上收后：

- canon 只写机制与最小约束
- 项目侧写差异与例外
- 不复制 canon 正文到每个项目

## 项目状态

| 状态 | 含义 | 规则改动 |
|---|---|---|
| `active` | 正在开发 / 维护 | 正常增删改；契约类改动整族刷新 |
| `dormant` | 暂停维护 | 只允许整体刷新；禁止零散改规则；AI 只做被要求的改动 |

`dormant` 项目不追新规范，不顺手重构。

## AI 的权限

| 规则类型 | AI 可以做什么 |
|---|---|
| 事实型 | 可直接改，但必须来自生成源 |
| 约束型 | 给 diff，等人确认 |
| 判断型 | 只给选项、代价、反例；不单独定稿 |

AI 可以起草 / 改写规范正文，但最终责任人必须是人。

## 不写度量快照

禁止写：

- “某字段共 81 处”
- “页面共 23 个”
- “本月新增 12 条规则”

改写为查询命令：

```bash
rg -n "pattern" src
```

需要趋势时，写采集方法与口径，不写一次性数字。

## 复查流程

1. 列出所有判断型规则与到期日。
2. 过期项：标“过期”，降级为参考。
3. 被违反最多的规则：考虑转成约束型（机检）。
4. 跨项目重复三次的规则：评估上收 canon。
5. 失效 / 无人维护的规则：删除，不留“历史口号”。
6. 更新 `AGENTS.md` 红线与索引。

## 反模式

- 规则只有“必须”，没有检查方式
- 判断型规则没有 owner / 日期
- 事实型字段手写，源码改了文档不改
- 例外没有到期，永久存在
- 每个项目复制一份 canon
- dormant 项目还在零散改规则
- AI 直接把判断型规则改成硬门禁
