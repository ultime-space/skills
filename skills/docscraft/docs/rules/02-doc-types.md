# 文档类型

> 用途：先判断“读者要解决什么”，再决定写成什么形态。
> 口径：一篇文档只承担一种主要类型；混合类型拆开或加指针。

## 七种类型

| 类型 | 读者的问题 | 形态 | 放哪 |
|---|---|---|---|
| 上手 Tutorial | “我第一次用，怎么跑起来？” | 一步步、可完成、有结果 | `README` / `docs/getting-started` |
| 操作 How-to | “我要完成 X，步骤是什么？” | 目标任务、前置条件、步骤、验证 | `docs/` / 场景文档 |
| 查阅 Reference | “这个字段 / 参数 / 命令是什么？” | 表、清单、契约、生成物 | `rules/` / API 文档 |
| 理解 Explanation | “为什么这样设计？” | 背景、取舍、边界、图示 | `docs/architecture` |
| 决策 ADR | “当时为什么选它？” | 背景、选项、决定、后果 | `docs/adr/` |
| 变更 CHANGELOG | “这一版改了什么？” | 用户可见变更、版本、日期 | `CHANGELOG.md` |
| 索引 Index | “我该先读哪几个文件？” | 路径、顺序、一句定位 | `README` / `AGENTS` / `llms.txt` |

## 选择顺序

1. 读者是要“学会”“完成”“查”“理解”“追溯决策”，还是“找入口”？
2. 如果是“查”，优先做生成物或表格，不写散文。
3. 如果是“理解”，先写结论与取舍，再给证据。
4. 如果是“完成”，必须写前置条件、步骤、验证。
5. 如果是“入口”，只放指针与红线，不塞正文。

## 各类型的硬要求

### 上手

- 有可复现的前置条件（Node / 包管理器 / 环境变量）
- 步骤可照着做，不需要先读完整架构
- 最后给出“成功时应该看到什么”
- 不夹参考手册、不夹设计哲学

### 操作

- 标题写任务，不写模块名
- 写清“什么时候用 / 什么时候不用”
- 每步有命令或文件路径
- 有验证步骤与失败排查

### 查阅

- 事实型内容优先从源码 / 类型 / 配置生成
- 每个字段写清类型、默认值、来源
- 标注版本或适用范围
- 不写教程与营销

### 理解

- 先给结论，再给背景与取舍
- 画边界：什么属于这一层，什么不属于
- 给出反例 / 不适用场景
- 不复制代码细节；代码用链接

### 决策

- 一条决策一条记录
- 写背景、选项、决定、后果、状态
- 新决策 supersede 旧决策，不改写历史
- 不把现行规范全文复制进 ADR

### 变更

- 只写用户可见变化
- 分类：新增 / 变更 / 修复 / 移除
- 关联版本与日期
- 不写内部重构流水账

### 索引

- 只放“先读什么”和一句定位
- 不复制正文
- 链接可点击、路径可打开
- 定期检查死链与失效入口

## 混合类型的处理

| 混合 | 处理 |
|---|---|
| 教程里夹参考 | 教程只留步骤；参数表移到参考，加链接 |
| 参考里夹解释 | 参考只留事实；为什么放“理解”或 ADR |
| 操作里夹决策 | 操作只留步骤；决策放 ADR，加一句“为什么见 ADR-00x” |
| README 里夹全部 | README 留快速开始与索引；细则移到 rules / docs |

## 判断示例

- “页面目录结构是什么？” → 查阅，放 `rules/pages.md`
- “为什么页面不能直接调 API？” → 理解，放 `docs/architecture` 或 ADR
- “怎么新增一个页面？” → 操作，放 `docs/` 或 `rules/pages.md` 的操作段
- “第一次跑项目？” → 上手，放 README
- “为什么选 Pinia 不选 Vuex？” → 决策，放 ADR
- “v1.2.0 改了什么？” → 变更，放 CHANGELOG

## 反模式

- 一篇文档同时叫“指南 / 规范 / 教程 / 参考”
- 参考文档里写“我们认为”
- 教程要求读者先理解完整架构
- ADR 里复制规则正文
- CHANGELOG 写成 commit 列表
- 索引用大段摘要代替链接
