# 设计批评

## 目标

在规范评审之外，判断设计是否好用、清楚、有气质；给出证据、分数与可执行建议。不改变规范结论。

## 输入

- 页面 / 组件 / 流程；需要时附截图、任务路径、目标用户。
- 先确认场景与品牌语气，避免用同一把尺子评价所有设计。

## 维度

| 维度 | 问题 | 证据 |
|---|---|---|
| **层级** | 第一眼看到什么？是否是该看的东西？ | 截图 + 3 秒回忆 |
| **信息架构** | 分组是否合理？导航是否可预测？ | 任务路径 / 卡片分类 |
| **认知负荷** | 一屏要记多少东西？是否可以渐进披露？ | 任务步数 / 选项数 |
| **情绪 / 气质** | 是否符合品牌与场景？ | 关键词对照 |
| **工艺** | 对齐、间距、图标、文案是否一致？ | 逐项截图 |
| **原创性** | 是否像模板 / 默认审美？差异点是否有理由？ | 与常见默认对照 |

## 步骤

涉及类型倾向时，先按 [`docs/project-types.md`](../docs/project-types.md) 取类型与角色；类型只调权重，不替代维度评分。

1. 明确场景、用户、主任务与最坏内容。
2. 按维度逐项打分（1–5），每项附证据。
3. 区分「问题」与「偏好」：问题要能说明影响，偏好只作建议。
4. 给 before / after 建议：改什么、为什么、代价是什么。
5. 与规范评审分开写；不用分数推翻可访问性结论。

## 输出

按 [`templates/critique-report.md`](../templates/critique-report.md)：

- 总体判断
- 维度分数与证据
- 主要问题（按影响排序）
- 建议（改什么、为什么、代价）
- 不在本次范围

## 反例

- 只给分数，不给证据。
- 把「我不喜欢」写成「设计错误」。
- 用「更高级」「更有呼吸感」这类无法执行的话。
- 用设计批评推翻对比度 / 焦点 / 热区等规范结论。
