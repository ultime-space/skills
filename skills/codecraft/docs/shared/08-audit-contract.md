# 审计输出契约 v1

> 2026-10-27 · v1
> 用途：约束 Audit 模式的判定、证据、局限与一致性，防止把“静态检查 0 findings”写成“全部通过”。
> 范围：JS/TS 项目；前端与后端共用本契约，规则解释分别在 `docs/frontend/09-audit.md` 与 `docs/backend/13-audit.md`。
> 关系：流程见 `docs/shared/02-ai-contract.md`；格式见 `prompts/output.md`；规则正文见 `docs/shared/00-constitution.md`。

## 1. 必填结构

Audit 报告必须包含：

1. **范围与方法**：仓库 / 分支 / 目录、技术端（前端 / 后端）、只读声明、执行的命令、未执行项与原因。
2. **逐条判定**：按该端规则集合全覆盖；不适用写 `na` 并说明原因。
3. **差距 / 风险**：按优先级分组，每条带证据。
4. **计划**：阶段、内容、可回滚、验收。
5. **验证**：命令 + 结果；不能跑要写原因。
6. **局限**：静态检查覆盖不到的部分。

逐条判定表固定为：

```md
| ID | 判定 | 证据 | 局限 |
|---|---|---|---|
| A4 | warn | `useList.ts` 6 处、页面 20+ 处 `code === 200` | 未覆盖运行时错误分支 |
```

## 2. 判定口径

| 判定 | 含义 |
|---|---|
| `pass` | 有证据覆盖该规则，且没有相反证据 |
| `pass（静态）` | 只有静态检查通过；必须写清检查范围，不能替代人工抽样 |
| `warn` | 存在相反证据、覆盖不完整，或只有部分满足 |
| `fail` | 明确违反，且会造成安全、数据或契约风险；按 P0 处理 |
| `na` | 该规则不适用；必须写原因 |

证据要求：

- 文件级：`path/to/file.ts:line`；不要只写目录。
- 命令级：写出命令与结果；计数必须带可复现的检索式。
- 禁止「看起来一致」「整体规范」这类无证据结论。
- 一个规则有多个子项时，逐项给证据；不能用一个子项代表全部。

**局限列固定写法**（便于横向比较不同仓库的报告）：

| 场景 | 写法 |
|---|---|
| 只做了静态检查 | `人工抽查：<目录 / 文件>；未覆盖 <...>；静态未命中不等于通过` |
| 只做了模式扫描 | `扫描范围：<目录 / 扩展名>；未覆盖 <...>` |
| 未执行命令 | `未执行 <命令>：<原因>` |

## 3. 优先级

| 级别 | 定义 | 例子 |
|---|---|---|
| P0 | 安全、数据丢失、不可回滚 | 密钥泄漏、越权、破坏性迁移 |
| P1 | 架构 / 契约 / 文档真源错误 | 分层失效、规范写错事实、门禁缺失 |
| P2 | 可维护性 / 重复实现 | 业务错误码散落、上传目录三份真源 |
| P3 | 测试、清理、体验 | 纯函数无单测、命名不统一 |

同一份报告里，P1 不能多于结论总数的一半而不说明取舍；否则先合并根因。

## 4. 计划表

```md
| 阶段 | 内容 | 可回滚 | 验收 |
|---|---|---|---|
| 0 | 文档纠偏 | 纯文档，单 commit 可回退 | 描述与检索结果一致 |
| 1 | 门禁补齐 | 移除 config / hook 即恢复 | 故意引入类型错误会被拦 |
```

要求：

- 每阶段可独立回滚，不用“重来一遍”。
- 验收必须是可执行命令或可检索结果，不写“感觉完成”。
- 不写时间估算；写依赖与顺序。
- 重构阶段先补基线（typecheck / 单测 / 契约测试），再改行为。

## 5. 交付前自检

- [ ] 该端规则全部出现，或写明 `na`
- [ ] 每条 `pass` / `warn` 都有文件行号或命令
- [ ] 所有计数都能用文中命令复现
- [ ] 已做一致性检查，没有把静态检查结果当成结论
- [ ] 已写明静态检查覆盖不到的部分
- [ ] 没有密钥、内部路径、客户隐私
- [ ] Audit 只读；未改代码、未起服务
- [ ] 计划每阶段可回滚、有验收
