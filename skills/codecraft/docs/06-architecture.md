# 代码架构设计方法（可选）

> 用途：系统级 / 模块级 / 演进级的代码架构决策方法；代码级模式见 `05-patterns.md`。
> 边界：只讨论代码架构；业务能力、角色、业务流程、领域规则不在本 skill 范围。
> 产出：只出文档时用 `scenarios/architecture-report.md` + `templates/architecture-report.md`。
> 原则：**方法先于模式；约束先于图；边界先于抽象。**
> 范围：方法本身与语言无关，可用于 JS/TS 前端与 Node 后端；文中目录与框架取舍以 JS/TS 为准。
> 术语：English（中文）。

## 0. 先分开六个词

| 词 | 一句话 | 产出 |
|---|---|---|
| **Architecture（架构）** | 系统的结构 + 约束 + 决策理由 | 模块、依赖方向、public API、ADR、验证规则 |
| **Architecture Style（架构风格）** | 可复用的结构方案 | 分层、模块化单体、六边形、事件驱动… |
| **Design Pattern（设计模式）** | 代码级解法 | Strategy、Adapter、State…（见 `05-patterns.md`） |
| **Method（方法）** | 产出架构的过程 | 目标 → 质量场景 → 边界 → 规则 → 验证 |
| **View（视图）** | 面向某类关注点的投影 | Context / Container / Runtime / Deployment |
| **Tactic（战术）** | 为某个质量属性做的局部决策 | 缓存、限流、重试、冗余 |

> **Fitness Function（适应度函数）**：把架构约束写成可自动执行的检查（lint / test / 指标 / 预算）。

### 0.1 什么才算架构决策

同时满足三条才值得记录：

1. **难逆转**：回退成本高（数据模型、部署单元、公共 API、技术栈）。
2. **影响面大**：跨模块、跨团队、跨生命周期。
3. **有取舍**：不是唯一解，换方案会得到不同代价。

命名、目录微调、单个组件实现是规范问题，不是架构决策。

### 0.2 架构的第一目标

- **让变化便宜**：改一个需求最多动一族（M4）。
- **让错误可见**：依赖方向、边界、失败模式能被检查（M5）。
- **让新人 / AI 可导航**：命名、目录、public API 能读出骨架（A13 / A16）。

## 1. 三个档位

| 档位 | 触发条件 | 产物 | 方法 |
|---|---|---|---|
| **L0** 单文件 / 原型 / 脚本 | 需求探索期、一次性 | 目录约定 + 一张上下文草图 | 命名 + 边界常识 |
| **L1** 多页应用 / 小团队 | 要交付、维护 3 个月以上 | Context + Container + 模块边界 + 依赖规则 + 3–5 条 ADR + 关键 fitness | 轻量七步法 |
| **L2** 多团队 / 长期 / 强合规 | 多团队、独立部署、强质量属性 | 完整文档骨架 + 质量场景 + 上下文映射 + 全量 fitness + 演进路线 | 质量属性驱动 + 场景评估 |

> 默认 L0；有真实触发才升级（A14 / A18）。**档位不是能力等级，是工程量。**

## 2. 轻量七步法

1. **写一页目标与约束**：3 条质量目标、3 条硬约束、1 条「不做什么」。
2. **画两张图**：System Context + Container；不画类图。
3. **列变化轴**：业务、平台、团队、部署、数据；每条写「多久变一次、谁推动」。
4. **切边界**：先按变化轴，再按数据所有权，最后按团队；用「删掉它谁会塌」检验。
5. **定依赖规则**：谁能 import 谁、public API 在哪、禁止环 / 跨层；写成 lint / CI。
6. **选模式**：只对已经疼的力选；一次只引入一个；写替代方案与退出条件。
7. **记录与验证**：ADR（难逆转的）+ fitness function（能自动的）+ 定期场景走查。

**不要做**：

- 需求未稳定就定最终架构；先用 walking skeleton（可走通的骨架）验证。
- 只有一个消费方就抽公共层 / 公共包。
- 团队 < 5 人、部署不痛，就上微服务 / 微前端。
- 没有自动验证手段，却写一堆「必须遵守」的规则。
- 为「以后可能」预建层。

## 3. 图：最小集

| 视图 | 回答 | 读者 | 不该出现 |
|---|---|---|---|
| **System Context** | 系统是什么、谁用、连哪些外部系统 | 所有人 | 技术选型、内部模块 |
| **Container** | 有哪些进程 / 应用 / 存储，怎么通信 | 技术、运维 | 类、函数 |
| **Component** | 容器内有哪些组件、职责、依赖 | 开发 | 具体实现 |
| **Code** | 类 / 接口级 | 开发（按需） | 通常不画，交给 IDE |

- 多数项目 **Context + Container 足够**；Component 只在边界说不清时画。
- 图要**跟着代码走**：能由图生成就不手绘；不能生成就在 CI 里比对。
- 图不覆盖质量属性与决策理由，所以必须配 ADR。

## 4. 切边界

### 4.1 三个切法，按顺序

1. **变化轴**：什么一起变、什么独立变。
2. **数据所有权**：谁是唯一写入者；数据边界比代码边界难改。
3. **团队边界**：谁维护、发布节奏是否一致（Conway）。

> 上下文边界 ≠ 团队边界 ≠ 部署边界；三者可以不同，但要对齐考虑。

### 4.2 边界是否成立（五问）

- 删掉这个模块，谁会塌？（M1）
- 改一个需求，要动几个模块？> 3 个就检查切分。（M4）
- 核心逻辑能否不启动框架就测试？（A2）
- 有没有循环依赖？有环 = 边界没切好。
- 数据归谁？谁是唯一写入者？

### 4.3 前端默认结构

```text
src/
  app/        组合根：路由、provider、全局错误、启动
  pages/      路由级页面（薄）
  features/   业务能力（垂直切片：ui + model + api）
  entities/   领域实体（可选）
  shared/     ui 原语、lib、api 客户端、config、types
```

- 依赖只能向下；同层不互相 import；跨模块只走 public API。
- 结构默认与框架无关：原生能表达的先写原生，Vue / React 只作页面与组件的落点。
- `shared/api` + adapter + interceptors 是承重墙，不塞进 feature。
- server state 与 client state 分开：server state 用 query 层；client state 用 store / 状态机。
- 测试分层：纯 core 单测 → feature 行为测试 → 页面 smoke → API 契约测试。

### 4.4 上下文关系（选型）

| 关系 | 一句话 | 代价 |
|---|---|---|
| Partnership（伙伴） | 两个上下文同生共死 | 协调成本高 |
| Shared Kernel（共享内核） | 共享一小块稳定模型 | 一改全动 |
| Customer-Supplier（客户-供应商） | 下游提需求，上游排期 | 上游可能不响应 |
| Conformist（遵奉者） | 下游直接遵从上游模型 | 下游失去表达力 |
| Anti-Corruption Layer（防腐层） | 下游加翻译层 | 多一层映射 |
| Open Host Service（开放主机服务） | 上游提供稳定公开协议 | 协议治理 |
| Separate Ways（各行其道） | 不集成 | 重复建设 |

## 5. 依赖规则与 fitness function

> 先有约束，再有检查；不要为了工具造规则。规则**少而硬**：10 条能执行的，胜过 50 条写在文档里的。

| 约束 | 检查方式 |
|---|---|
| 依赖方向：核心不 import 上层 | dependency-cruiser / eslint boundaries |
| 分层：页面不直接调 API；UI 不 import 数据层 | `no-restricted-imports` |
| 公共 API：只能从入口导入，禁止深路径 | package `exports` + lint |
| 无环 | 依赖图检查 |
| 体积预算：首屏 / 单路由 chunk | size-limit / bundlesize |
| 性能预算：LCP / INP / CLS | Lighthouse CI |
| 契约：schema diff / consumer-driven | 契约测试 |
| 安全：依赖漏洞 / 密钥 / CSP | SCA + secret scanning |

- 拒绝用 `eslint-disable` 大面积绕过；例外必须登记（A10）。
- 架构腐烂信号：规则被大量禁用、例外失控、图与代码不一致。

## 6. 架构模式速查

### 6.1 组织形态

| 模式 | 一句话 | 何时用 | 何时不用 | 代价 |
|---|---|---|---|---|
| **Layered**（分层） | 按技术职责分层 | 职责清晰、传统应用 | 变化按 feature 走 | 层多、易千层饼 |
| **Feature-first**（按功能） | 顶层按业务能力切 | 业务变化快 | 强共享 / 强横切 | 跨 feature 重复 |
| **Vertical Slice**（垂直切片） | 一个功能从 UI 到数据一条竖片 | 功能独立 | 强事务、共享多 | 跨片重复 |
| **Modular Monolith**（模块化单体） | 一个部署单元，内部强边界 | 小团队、边界可稳定 | 需独立扩缩容 | 边界靠纪律 / lint |
| **Microservices**（微服务） | 独立部署、独立数据 | 多团队、独立扩缩容 | 小团队、事务复杂 | 分布式事务、运维 |
| **Micro-frontend**（微前端） | 前端按团队独立发布 | 多团队独立发布 | 单团队、组件复用 | 运行时 / 样式隔离 |
| **Microkernel / Plugin**（微内核 / 插件） | 核心最小，能力靠插件 | 多品牌、多平台 | 无插件生态 | 插件契约、版本治理 |

**默认**：个人 / 小团队 / 单产品 → 模块化单体 + feature-first（或垂直切片）；只有「独立发布 / 独立团队 / 独立扩缩容」真实存在时，才拆微服务或微前端。

### 6.2 边界与依赖

| 模式 | 一句话 | 适用力 | 代价 |
|---|---|---|---|
| **Clean Architecture**（整洁架构） | 依赖向内 | 长期、复杂业务 | 层多、映射多 |
| **Hexagonal**（六边形 / 端口与适配器） | 核心定义端口，外部用适配器 | 多外部系统、可替换 IO | 端口 ceremony |
| **Screaming Architecture**（会尖叫的架构） | 目录先喊业务，不喊框架 | 新人要一眼看懂 | 需要团队共识 |
| **BFF**（前端专属后端） | 每个前端一个聚合层 | 多端差异大 | 多一个服务 |
| **ACL**（防腐层） | 边界翻译外部模型 | 外部模型脏 / 会变 | 映射代码 |
| **Composition Root**（组合根） | 入口集中组装依赖 | 需要可测试、可替换 | 集中点易膨胀 |

### 6.3 数据与一致性

| 模式 | 一句话 | 何时用 | 代价 |
|---|---|---|---|
| **Database per Service**（每服务一库） | 服务独占数据 | 微服务 | 跨服务查询复杂 |
| **Saga**（长事务） | 本地事务 + 补偿 | 跨服务流程 | 补偿逻辑、幂等 |
| **Transactional Outbox**（事务性发件箱） | 业务数据与事件同事务落库 | 要可靠发事件 | 投递器、去重 |
| **CQRS**（命令查询分离） | 读写模型分开 | 读写差异大 | 双模型、延迟 |
| **Event Sourcing**（事件溯源） | 存事件流，状态重放 | 审计、可回放 | 事件版本、存储 |
| **Idempotency Key**（幂等键） | 重复请求结果一致 | 重试、支付 | 键管理 |

> 先定「谁是数据的唯一写入者」，再谈模块 / 服务。微服务的第一道裂缝通常是共享数据库。

### 6.4 演进

| 模式 | 一句话 | 何时用 | 代价 |
|---|---|---|---|
| **Strangler Fig**（绞杀者） | 新系统逐步包住旧系统 | 遗留迁移 | 双系统并存 |
| **Branch by Abstraction**（分支抽象） | 先加抽象层，再换实现 | 不能停的大改造 | 临时复杂度 |
| **Expand-Contract**（扩展-收缩） | 先兼容新旧，再删旧 | 数据 / API 迁移 | 两阶段窗口 |
| **Feature Flag**（特性开关） | 运行时开关 | 灰度、回滚 | 分支膨胀 |
| **Canary / Blue-Green**（金丝雀 / 蓝绿） | 小流量验证 / 双环境切换 | 高风险发布 | 监控 / 双倍资源 |

演进原则：不做大爆炸重写；每次迁移都要有回滚路径与验证指标；最小单位是「可独立验证的切片」。

### 6.5 前端五个轴（不要混着谈）

| 轴 | 选项 | 关键判断 |
|---|---|---|
| 渲染 | CSR / SSR / SSG / ISR / Streaming / Islands | 首屏、SEO、实时性、部署 |
| 路由 | 集中式 / 文件式 / 分布式 | 团队边界、发布独立性 |
| 数据 | REST / GraphQL / tRPC / BFF / 本地优先 | 聚合、缓存、离线 |
| 状态 | 局部 / 全局 store / server state / 状态机 | 生命周期、共享范围、异步复杂度 |
| UI 组合 | 单应用 / 微前端 / 设计系统分层 | 团队规模、复用范围、品牌数量 |

## 7. ADR

```md
# ADR-0001: 采用模块化单体而非微服务

- Status: Accepted | Superseded by ADR-0005 | Deprecated
- Date: 2026-10-26
- Deciders: ...
- Context: 3 人团队、单产品、部署不痛；微服务会引入分布式事务与运维成本。
- Decision: 先做模块化单体，模块间只通过 public API 通信；预留按模块拆出的可能。
- Consequences: 边界靠 lint 维持；未来拆分需要先做数据所有权梳理。
- Alternatives: 微服务（运维成本高）、大泥球（不可接受）。
```

- **append-only**：不删、不改历史；被取代就标 `Superseded`。
- 放在代码仓里，跟代码一起 review。
- 只记**难逆转**的；可逆决策用 RFC / PR 描述。
- 每条必须有 **Consequences** 与 **Alternatives**；没有代价说明的决策不算记录。
- 反模式：**Documentation Theater（文档剧场）**——只写「未来的人会问为什么」的那部分。

## 8. 反模式

| 反模式 | 表现 | 后果 | 替代 |
|---|---|---|---|
| **Big Ball of Mud**（大泥球） | 没有边界 | 改一处崩一片 | 切模块 + 依赖规则 |
| **Distributed Monolith**（分布式单体） | 拆了服务，仍共享库 / 强耦合 | 两头不讨好 | 先模块化单体，按数据所有权拆 |
| **Cargo Cult**（货物崇拜） | 抄大厂架构不看前提 | 水土不服 | 先问约束 / 团队 / 规模 |
| **Resume-Driven Development**（简历驱动） | 为用新技术而用 | 复杂度失控 | 按力选型，写代价 |
| **Ivory Tower**（象牙塔） | 架构师不写代码 | 设计与实现脱节 | 伴随实现 |
| **Diagram-Driven**（图驱动） | 图漂亮，代码没约束 | 图与代码两张皮 | 图 + lint + ADR |
| **Over-layering**（千层饼） | 每层只转发 | 认知 / 维护成本 | 合并层，按变化切 |
| **Architecture by Implication**（默认架构） | 没人决策 | 隐性耦合 | 显式 ADR + 边界 |
| **God Module**（上帝模块） | 一个模块什么都知道 | 难改、冲突多 | 按职责拆 |
| **Cyclic Dependency**（循环依赖） | A→B→A | 无法独立测试 | 提共享层 / 依赖倒置 |
| **Premature Platform**（过早平台化） | 1 个产品就建平台 | 平台没用户 | 第二个产品出现再平台化 |
| **Folder Architecture**（目录即架构） | 只分目录，没有规则 | 目录好看，耦合照旧 | 依赖规则 + public API |
| **Monorepo as Architecture**（同仓即解耦） | 以为一个仓就自动解耦 | 隐式耦合依旧 | 包边界 + 依赖规则 |
| **AI-Generated Entropy**（AI 生成熵） | AI 复制最近的模式 | 同族不同形、边界漂移 | 约束 + 正面样例 + lint |

## 9. 评审清单（12 条）

1. 每个模块能用一句话说清职责？
2. 依赖是否单向、无环？
3. 核心逻辑能否脱离框架 / 网络 / UI 测试？
4. 每份数据是否有唯一写入者？
5. 新增一个功能要改几个模块？> 3 个就检查切分。
6. 换平台 / 渠道要改几处？差异是否收在边界？
7. 失败模式是否明确：超时、重试、降级、幂等？
8. 是否有 public API？能否禁止深路径 import？
9. 难逆转决策是否有 ADR：替代方案 + 代价 + 退出条件？
10. 约束是否可自动验证？规则是否少而硬？
11. 每个引入的模式是否有退出条件？
12. 是否只有一个消费方就抽象了？是否预建了「以后可能」的层？

## 10. AI 协作下的架构

- 架构是 AI 的**上下文压缩器**：边界清晰 → 搜索空间小 → 生成稳定。
- AI 会复制最近的模式：坏架构会被放大；先修边界，再让 AI 写。
- 给 AI 的架构输入：目录树 + 依赖规则 + 1 个正面样例 + 1 个反例 + 禁止清单。
- **不让 AI 做架构决策**；让 AI 出「候选方案 + 代价表」，人拍板。
- 评审看 **diff 的依赖方向**，不只看代码风格。
